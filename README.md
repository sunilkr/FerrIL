## Usage

So far, this project is developed and tested on Windows(Win10+) only. In theory, it should work on other platforms by tweaking [profile](profile/src/main.rs) and _build_ tool.

.NET Framework 4.7 is the earliest version known to work with this implementation. A binary targeting .NET Framework 3 failed to load the profiler. Since the current version of profiling API is available from .NET Framework 2.0 runtime, profiler should have worked in-thory.

For details on specific modules, please see [docs](./docs/) folder.

### Building

Use `cargo` to build the project. Following `cargo` aliases exist to build 32bit binaries for Windows (see [config.toml](.cargo/config.toml)) in `target\i686-pc-windows-msvc\<debug|release>\` path.

* `cargo bd32`: Build 32 bit _debug_ version
* `cargo br32`: Build 32 bit _release_ version

#### Build Artefacts:

A successful build should results in following artefacts:
* `profile.exe`: This utility set-ups environment variables required for profiling
* `ssl_unpin.dll`: These DLLs implement CLR profiling APIs to bypass SSL Server Certificate verification
* `tracefn.dll`: Experimental profiler for dumping selected function call arguments
* `asmdump.dll`: Dumps embedded assembly loaded at runtime by the application. 
* `test_profilers.dll`: Very basic profiler for testing.

### Runnig:

Simplest way is to use `profile.exe` utility which takes profiler path and the target .NET application. Use help (`profile.exe -h`) for details. A the very least you need to use `profile.exe <TARGET>` to load `test_profilers.dll`. Profiler DLL path is assumed relative to `profile.exe`. Log messages generated by profiler are logged into `clr-profiler.log`. 

Command examples:
1. `profile sample.exe`: Execute `sample.exe` with `test_profilers.dll` profiler attached.
2. `profile.exe -s -l debug -p tracefn.dll sample.exe`: Execute `sample.exe` in _suspended_ mode, allowing debugger to be attached. _tracefn.dll_ profiler is attached. Set log level to _debug_.

### Limitations:

1. Killing (Ctrl+c) `profile.exe` does not kill child process.
1. Logs may not be shown on console for GUI apps. Check log file (default is `clr-profiler.log`).
1. .NET Dlls are not supported yet.

## CLR Profiling flow:
1. Some COM client (CLR in this case) calls `DllGetClassObject`, which populates a pointer (`[out] **ppv`) to an instance of a struct that adheres to `IClassFactory`.
1. The COM client then calls `CreateInstance` on the `IClassFactory` that it now has a handle to. This populates a pointer ([out] parameter) to an instance of a struct that adheres to `ICorProfilerCallback9`.
1. The COM client calls `Initialize` on the `ICorProfilerCallback` instance and provides an instance of `ICorProfilerInfo`, which profiler can use to call into .NET runtime.
1. Profiler instance calls `SetEventMask` on ProfilerInfo instance to subscribe to the events its is interested in.
1. Based on the EventMask provided in last call, CLR calls methods defined by `ICorProfilerCallback` interface.
1. Callbacks for handing function calls and stack walk are global and not part of `ICorProfilerCallback` interface. This makes maintaining state across call tricky, specially when golbal/static variables shared among threads are not tirivial. These functions also have with their own set of limitations.

## Project Structure

Following are core crates of this project.

* clr_profiler: Library implementing CLR profiling API and interop/FFI functionality
* clr_profiler_macros: Utility `proc-macro`s to simplify usage.
* log_init: Library to initialize logging infrastructre.
* profile: Loader executable to attach profiler to .NET runtime.

Other than these, most crates are profiler implementations dealing with spcific use cases, or test functions.
